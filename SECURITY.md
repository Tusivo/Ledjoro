# Security model

Accounting data is sensitive and high-value. This document states what Ledjoro defends against, how, and what it does **not** (yet) cover.

## Design principles
- **Minimal attack surface:** zero third-party runtime dependencies (no supply-chain exposure); one SQLite file; no outbound network calls; no telemetry; **no browser, web view or HTML rendering** (the window is native Windows controls, so there is no page for a script to run in).
- **Secure by default:** the engine listens on loopback only and refuses every request that lacks a secret key only the app knows; strict response headers; no CORS.
- **Defence in depth:** every rule is enforced in code *and* (for ledger immutability, audit append-only, amount sanity) by the database.
- **Data minimisation:** tax IDs/SSNs are neither stored nor imported; passwords are never logged; request bodies are never logged.

## Controls

| Threat | Control |
|---|---|
| Password theft / guessing | scrypt (N=32768, r=8, p=1, per-user salt); 12+ char policy, common/repetitive/username checks; constant-time compare; dummy-hash for unknown users (no user enumeration by timing); identical error messages; per-IP limiter (30/15 min) + per-account escalating lockout (60 s → 1 h) |
| Session theft / fixation | 256-bit random token; **only its SHA-256 is stored**; HttpOnly + SameSite=Strict (+ Secure and `__Host-` prefix over HTTPS); new session on every login; 30-min idle and 12-h absolute expiry; all sessions revoked on password change, disable, or role change |
| CSRF | SameSite=Strict **and** per-session CSRF token header (constant-time check) **and** Origin / Sec-Fetch-Site validation on every state-changing request |
| Other programs or web pages talking to the engine | The app starts the engine with a random per-launch key (256-bit) and a random loopback port. **Every** request must carry the key (compared in constant time; 403 otherwise), so another program on the machine, or a web page in any browser sending requests to localhost, gets nothing. The engine refuses to start at all without a key, and exits when the app closes its stdin |
| DNS rebinding / host spoofing | Host header allow-list (421 otherwise) |
| XSS / clickjacking | Not applicable by design: there is no web UI. The app draws text with native controls (never parses HTML), and the engine serves only JSON with `default-src 'none'`, `frame-ancestors 'none'` and nosniff |
| SQL injection | Prepared statements with bound parameters only; no string-built SQL from input |
| Broken access control | Server-side permission check on every route; role permissions re-read per request (changes apply immediately); per-kind write checks (sales vs purchases); last-administrator protection; users table is not exportable |
| Malicious import files | Size cap (10 MB), row cap, JSON/CSV/XML parsers hardened: **no DTD / entity expansion (XXE impossible)**, depth and node caps, no `eval`, no filesystem access from file contents, quoted-field validation; parse → *plan* (read-only) → commit in a **single transaction**; invalid files change nothing |
| CSV/formula injection | Exports prefix `'` to cells starting with `= + - @` or tab/CR |
| Data tampering / fraud | Posted entries are immutable (DB triggers); corrections are reversals; **hash-chained audit log** (append-only triggers; `Verify integrity` detects edits/deletions); closing date blocks back-dated changes; import is idempotent via content hashes |
| Resource exhaustion | Body-size limits (413), request/header timeouts, per-IP API rate limit, limited list sizes |
| Info leakage | Generic 500s; errors logged without bodies; `Cache-Control: no-store` on API; no stack traces to clients |
| Lost password / lockout | A **recovery key** (100 bits of randomness) is shown once, stored only as a scrypt hash, works once (a new key is issued on use), is rate-limited (10 tries / 15 min / IP) and shares the escalating account lockout. Resetting revokes every session. Regenerating a key needs the current password |
| Credential handling at setup | The sign-in sheet keeps the password and key only in the page's memory, masked until you choose to reveal or print; nothing is written to storage, logs or the URL. A bright red reminder tells users to vault or print it and store it safely |
| Weak or phished passwords | Optional **passkeys** (WebAuthn / FIDO2): sign in with Windows Hello, a phone or a security key instead of a password. The engine issues a one-time 256-bit challenge (3 minutes, single use) and checks the answer itself: the challenge, the program id hash, that the person was present **and verified** (PIN, fingerprint or face is required), the signature (ES256, RS256 or EdDSA), and that the signature counter only goes up (a copied key is refused). Adding one needs the current password. Only the public key is stored, so a stolen database cannot sign in. Disabled or locked accounts cannot use a passkey. The Windows prompt is shown by Windows, not by Ledjoro |
| Recovery QR code | The QR code on the recovery sheet contains the company name, username and **recovery key**, exactly the secrets the sheet already prints, so it must be treated like the sheet: on screen it stays hidden until "Show secrets", and printed copies belong in the same safe place. It never contains a password. Scanning is done locally with Windows' own camera API: frames are examined in memory and discarded (never written to disk or sent anywhere), only codes that start with the Ledjoro recovery prefix are accepted, and a code for a different company asks before switching. The reset itself is unchanged: the same rate limits, single-use key and lock-out apply, and a new password and a new recovery key are issued |
| Automatic backups | Written by the engine process itself, so no password is kept anywhere to make them. They are protected exactly like hand-made ones: locked with the recovery key (the key is never stored, only the wraps that already exist), or unlocked only if the user explicitly chooses "Not locked", which the page warns about. A passphrase cannot be used because it would have to be stored. The folder is chosen by someone with the `settings.manage` permission and is test-written first; files are written under a temporary name and renamed, and only files Ledjoro named `ledjoro-auto-*.obbak` are ever pruned |
| Reconciliation, matching | Cleared and matched states live in separate tables (`reconciled_lines`, `bank_transactions.entry_id`), so journal entries stay immutable. The server re-checks every ticked line (right account, not already cleared, not dated after the statement) and that the total equals the statement to the cent inside one transaction before saving; each action is written to the hash-chained audit log |
| QuickBooks Web Connector link | Off by default. When switched on, the engine opens a second listener, bound only to 127.0.0.1 and ::1 (never the network), that accepts nothing except the Web Connector's SOAP calls and refuses any other `Host` header (DNS-rebinding defence). It has its own credentials, separate from the app's launch key and from user passwords: a random username and a random 120-bit password, shown once, stored only as a scrypt hash, replaceable at any time (which also ends open sessions); ten wrong passwords in ten minutes are refused for the rest of that window. Sessions use random one-time tickets and only one runs at a time. The connection file the Web Connector reads contains no password. It asks for standard access, because the Web Connector itself has to record an identifier in the company file (QuickBooks refuses that for read-only programs); Ledjoro never sends anything but queries. Ledjoro only ever sends *query* requests to QuickBooks (a test asserts there is never an Add, Mod or Del request). Incoming XML goes through the same hardened parser as file imports (DTDs and entities are never processed, nesting and size are capped), and request bodies are capped at 128 MB. What is received is only held in memory as a preview; it enters the books through the normal import path (balanced entries, de-duplication, audit log, undoable) after an explicit click, and enabling, disabling, new passwords and imports are written to the audit log |
| Watched download folder | Read-only: Ledjoro only reads files with the extensions .qbo, .ofx and .qfx (up to 10 MB each) directly inside the folder the user chose, and never moves, edits or deletes them. A file is parsed by the same hardened statement reader used for manual imports, shown as a preview, and imported only when the user presses Import. Import looks the file up by its SHA-256 hash from the list the folder scan produced, re-checks that its real path (symlinks resolved) is directly inside the chosen folder and that its content still hashes the same, so a file swapped after being listed is refused and no path from the screen is ever opened. Dealing with a file is written to the audit log |
| Backup theft / lost backup | Backups are **AES-256-GCM** with a fresh random key per backup. That key is wrapped two ways: by the company's **recovery key** (scrypt) and, optionally, by a passphrase, so either opens the file and a forgotten passphrase is not fatal. The header is authenticated; editing it or the data is detected. A person may also choose **no encryption**, which is clearly warned about on screen and in the audit log. A backup is made only after the current password is confirmed |
| One company reading another's books | Each company is a separate folder with its own database, users, passwords, recovery key, setup token and engine process; switching companies stops one engine and starts another, so nothing is shared in memory or on disk |
| Local file exposure | DB file/dir created with restrictive modes (best effort on Windows); the engine serves no files at all (any non-`/api/` path is a 404) |
| Outside edits to the books file | **Held exclusively while Ledjoro runs**: another program (a database browser, a script) that tries to read or write the file gets "database is locked". The data folder's permissions are limited to the current Windows user and SYSTEM (inherited permissions removed; done in checked steps and undone if it would lock the user out). A read-only flag is cleared at start. At **every start** the file is verified (`quick_check`, the hash-chained activity log, balanced ledger) and any problem is shown on screen after sign-in. **Limits, stated plainly:** Windows cannot stop the account that owns the folder from overwriting bytes in a file it can open, and while Ledjoro is closed the file is an ordinary file, so edits are *detected* (most tampering breaks the activity-log chain or the ledger balance), not prevented. Real prevention needs encryption of the database with a key only the program holds, which is a roadmap item |
| Tampered engine | The engine inside `Ledjoro.exe` is unpacked to `Ledjoro-Data\engine\<hash>\` and its SHA-256 is checked against the value built into the app on **every** start; a mismatch is re-extracted from the app |

Verified by automated tests in `test/` (55 tests) and by the app's own self-test (65 checks across every screen, dialog, import/undo, backup/restore and sign-in recovery): CSRF, origin, host, lockout, session expiry/revocation, RBAC, body limits, no files served, SQLi-as-data, CSV injection, XXE, immutability, audit tamper detection, import hostile-input handling.

## Hardening checklist (your computer)
1. Use your own Windows account with a strong Windows password, and turn on **BitLocker / device encryption**. The database is not encrypted by the app (see limitations), so the disk is what protects it at rest.
2. Make **encrypted backups** (*Settings - Data & backup*) on a schedule and **test a restore**. Keep backups off this computer.
3. Keep Windows patched. Give people the least-privileged role, disable leavers promptly, and review the audit log.
4. Use unique passphrases, keep the recovery key and backup passphrase in a password vault, and print the sign-in sheet only if you will store it somewhere safe.
5. Verify the SHA-256 of a downloaded `Ledjoro.exe` before first run. The exe is unsigned.

## How the app and engine talk
- The app starts the engine as a hidden child process on `127.0.0.1` with a random port, a random per-launch key and the one-time setup token passed through its **environment** (never the command line, never a URL, never a file).
- Sign-in, the CSRF token, roles and audit work exactly as before: the app keeps the session cookie and CSRF token in memory and sends the key with every request.
- **Trust boundary:** other programs running as the same Windows user could read the engine's environment or attach to its process. The app assumes the Windows account is trusted. On shared computers give each person their own Windows account.
- Diagnostics go to `ledjoro.log` in the data folder (no request bodies, passwords or tokens). If the app itself crashes, it writes `shell-crash.log` there.
- Release hygiene: the exe is unsigned and built by `npm run build` (`scripts/build-native.js`).

## Backups
- *Settings - Data & backup* makes a checked copy of the books (SQLite's online-backup API, then `integrity_check`) and saves it one of three ways: **locked with the recovery key** (recommended; nothing extra to remember), **locked with a passphrase you choose** (the recovery key also opens it), or **not locked**. The file starts with a random 256-bit data key; the data is AES-256-GCM encrypted with it, and the key is wrapped by the recovery key and/or the passphrase (scrypt). The plaintext temporary copy is deleted.
- **Which recovery key opens which backup.** A backup opens with the recovery key that was current when it was made, and with its passphrase if it has one. When a recovery key is replaced (after it resets a password, or when you make a new one), older backups still open with the older key, and newer backups need the newer one. Books created before this feature link their key once by typing it in the backup screen.
- Making a backup needs `settings.manage` and your current password, and is audit-logged with how it was protected.
- **Restore button**: needs `settings.manage`, your current password and typing `RESTORE`; a locked backup also needs its passphrase or a recovery key (an unlocked one needs neither). The file must decrypt and pass its safety check, pass the database integrity check, be a Ledjoro database of a supported version, and contain an active administrator. A safety copy of the current data is written first (locked with the recovery key when linked), the swap is a single transaction (the immutability triggers are dropped and recreated inside it), and every session is cleared. The restore is audit-logged.
- Older `OBBK1` backups (passphrase only) can still be restored. The command-line restore (`node src/cli.js restore`) refuses to overwrite an existing database.
- Undoing an import never rewrites history: it posts reversing entries, respects the closing date, and is audit-logged.

## Known limitations / roadmap
- **Passkeys are optional**, and the password (plus recovery key) remains as a fallback, so a passkey does not make the account passwordless-only. There is no separate second-factor requirement yet (TOTP is planned). The app is a single-computer program, so access control rests on the Windows account plus Ledjoro sign-in.
- The database is **not encrypted at rest** by the app (use disk encryption; SQLCipher-style encryption is the roadmap item that would make the file unreadable and un-editable without the program). Field-level encryption would be required before adding tax-ID storage.
- Rate limiter and lockout counters for IPs are in-memory (reset on restart); account lockout is persisted.
- One computer, one data file; there is no multi-computer sharing or high availability.
- The engine runs on Node.js (the V8 JavaScript runtime); keeping Windows and rebuilding with a current Node 24.x patch release covers its security fixes.
- Not independently penetration-tested or audited. Treat v0.1 as pre-production.
- Dependency-free means no vetted framework middleware; the HTTP layer is small and tested but bespoke.

## Reporting a vulnerability
Open a private security advisory with the maintainers (add contact details before publishing). Please do not file public issues for vulnerabilities.
